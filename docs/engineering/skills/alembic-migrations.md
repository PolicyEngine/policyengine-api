# Alembic Migrations

Use this skill whenever adding or changing SQLAlchemy models, Alembic
configuration, database schema, migration revisions, or code that connects to
a database.

## Mandatory generation rule

AI **MUST NOT manually author Alembic revision scripts**. Generate every schema
revision from reviewed SQLAlchemy metadata:

```bash
# API v1 / Cloud SQL MySQL
uv run alembic -c alembic-v1.ini revision --autogenerate -m "<description>"

# API v2-alpha / Supabase Postgres
uv run alembic -c alembic-v2.ini revision --autogenerate -m "<description>"
```

The mandatory generation operation is `alembic revision --autogenerate`.
Always select the configuration for the intended migration domain explicitly;
never use Alembic's default configuration discovery. The v1 configuration
keeps MySQL revisions in `migrations/v1`, while the v2 configuration keeps
Postgres revisions in `migrations/v2`.

If generated operations are wrong, first correct the model metadata and
regenerate. AI may make minimal post-generation corrections only for dialect compatibility,
reversibility, or an objectively incorrect autogenerated
operation. Document each correction and cover it with upgrade and downgrade
tests. Do not add arbitrary schema or data operations to a generated revision.

If the required migration cannot be expressed safely by autogeneration plus
those narrow review corrections, stop and request a human migration decision.

## Required checks

Before committing a migration, run these checks against the matching domain:

1. Run `uv run alembic -c <configuration> check` and review the generated
   schema operations.
2. Upgrade a fresh database to `head`.
3. Compare the database to the complete ORM metadata before release.
4. Downgrade one revision and upgrade to `head` again in an isolated database.
5. Confirm application startup performs no implicit DDL
   (`api.data.sqlalchemy-and-alembic-only` checks the code for it; see the
   next section).

Never print database credentials or embed them in Alembic configuration. The
deployed v1 database is already versioned; never recreate or restamp its
baseline. Missing or invalid revision history must fail closed for manual
recovery.

## Database access through SQLAlchemy and Alembic

Rule `api.data.sqlalchemy-and-alembic-only`: code connects to relational
databases only through SQLAlchemy engines, connections and sessions, never by
calling a database driver directly, and changes persistent schema only through
Alembic revisions.

- API v1 builds its Cloud SQL engine in `policyengine_api/data/orm.py`. The
  Cloud SQL connector is passed to `create_engine` as `creator=`, so SQLAlchemy
  opens and pools the connections. SQLAlchemy does not add its MySQL connection
  arguments to connections a `creator=` function opens, so the connector call
  passes MySQL's `CLIENT_FOUND_ROWS` flag in `client_flag` itself; with it an
  UPDATE reports the rows it matched rather than the rows whose values changed,
  which SQLAlchemy needs to check UPDATE row counts.
- API v2 builds its SQLModel engine from a `postgresql+psycopg` URL in
  `policyengine_api/data/v2/database.py`.
- Take connections and sessions from those engines, never from
  `psycopg.connect`, `pymysql.connect`, `sqlite3.connect` or another driver.
- Change schema only with an autogenerated revision (see "Mandatory generation
  rule"). Application code, scripts and CI never call `create_all`,
  `drop_all`, `Table.create` or `Table.drop`, build SQLAlchemy DDL constructs,
  call Alembic operations outside `migrations/`, or run `CREATE`, `ALTER`,
  `DROP` or `TRUNCATE` SQL.

`tests/unit/data/test_database_access_boundaries.py` checks `policyengine_api/`,
`scripts/`, `migrations/` and `.github/`, skipping tests and the paths the
rule's `migration-revision` exception names: the generated revisions under
`migrations/*/versions/`. It parses each module and reports:

- imports of `psycopg`, `psycopg2`, `pymysql`, `MySQLdb`, `mysql.connector`,
  `sqlite3`, `asyncpg`, `pg8000`, `aiosqlite` or `aiomysql`, including through
  `importlib.import_module`;
- access to the driver connection beneath SQLAlchemy: the `driver_connection`
  and `dbapi_connection` attributes and `raw_connection()`, and a driver
  connection's private attributes (pymysql's socket, `_sock`), read as an
  attribute or through `getattr`;
- `create_all()`, `drop_all()`, and `create()` or `drop()` on a table, index
  or sequence; SQLAlchemy DDL constructs such as `CreateTable`; and `op.*`
  calls or `alembic.op` imports outside `migrations/`;
- string literals, other than docstrings, that begin a `CREATE`, `ALTER` or
  `DROP` of a table, type, schema, database, index, sequence, view or
  extension, or a `TRUNCATE`.

### Declared exceptions

The rule's exceptions are its `[[rule.exception]]` entries in
`rules/registry.toml`, which the check reads. Each has a `path`, a `category`
and a `reason`:

- **`driver-access`** and **`schema-change`**: one construct in one file. The
  entry's `path` names the file and its `match` names the construct, exactly
  as the check reports it, such as `import psycopg.sql` or
  `call STAGING_METADATA.create_all()`.
- **`migration-revision`**: a path pattern the check doesn't scan at all.

The check fails on a construct no entry allows, on an entry with an unknown
category or a missing `match`, and on an entry that no longer matches anything,
so an exception can't gain a name or a file, and is removed once it's unused.
The entries:

1. **COPY through the driver connection** (`driver-access`, three entries).
   Publication writes rows with Postgres `COPY ... FROM STDIN`, which
   SQLAlchemy has no API for. `copy_rows` in
   `policyengine_api/data/v2/catalog/publication_staging.py` uses the psycopg
   connection beneath the Connection the publishing Session holds
   (`session.connection().connection.driver_connection`), which SQLAlchemy
   opened and still manages, so the transaction stays the Session's. It imports `psycopg.sql` to
   compose the `COPY` statement and `psycopg.types.json.Jsonb` to send JSON
   values.
2. **Temporary staging tables** (`schema-change`). `create_staging_tables` in
   the same module calls `STAGING_METADATA.create_all` for tables declared
   `TEMPORARY` with `ON COMMIT DROP`. Postgres drops them when the publishing
   transaction commits, so they are not persistent schema. The check confirms
   that every table on `STAGING_METADATA` compiles to
   `CREATE TEMPORARY TABLE ... ON COMMIT DROP`.
3. **The v1 pool's socket diagnostics** (`driver-access`). The listeners in
   `policyengine_api/data/orm_pool_events.py` that record the v1 Cloud SQL
   pool's connects, invalidations and closes read the file descriptor and
   local port of pymysql's socket, `getattr(connection, "_sock", None)`, from
   the driver connection SQLAlchemy's `connect` pool event passes them.
   SQLAlchemy has no API for a connection's socket, and the records need it to
   show whether a database reconnect reused or closed an HTTP connection's
   socket. The listeners never read or write through the socket or the driver
   connection, and import no driver.
4. **Alembic revisions** (`migration-revision`), `migrations/*/versions/*.py`.
   Revisions are where schema changes belong, and Alembic generates them, so
   the check doesn't scan them. Ruff skips the same files (`extend-exclude` in
   `pyproject.toml`).

A new exception is a rule change: add a `[[rule.exception]]` entry to the rule
in `rules/registry.toml`, explain here why SQLAlchemy or Alembic can't do the
job, and get it reviewed as one. `rules/` is code-owned
(`api.process.rule-machinery-code-owned`).

### Out of scope

Redis (`policyengine_api/runtime_cache/`) is a key-value cache, not a
relational database. This rule does not cover it.

### Related rules

- `api.data.runtime-sql-confined`: raw SQL stays in the data-access layer.
- `api.services.no-direct-queries`: services never query or open connections
  themselves; they call the data-access layer.
- `api.v2.single-orm-layer`: v2 models use SQLModel, with no second
  SQLAlchemy ORM layer.
- `api.migration.alembic-v1-qualified` and `api.migration.alembic-v2-qualified`:
  CI applies the v1 and v2 revisions to disposable MySQL and Postgres
  databases, and checks v2 for schema drift.
- `api.migration.alembic-autogenerated-only` (doc-only): revisions are
  autogenerated, never hand-written.
- `api.startup.no-import-side-effects`: importing v2 modules, starting up and
  serving a request open no network connections.
- `api.data.orm-only`: every statement runs through an ORM Session on mapped
  classes (see the next section).

## Database statements through the ORM

Rule `api.data.orm-only`: code that reads or writes database rows declares
tables only as SQLAlchemy ORM mapped classes, SQLModel classes included, and
runs every statement through an ORM `Session` against those classes. It never
uses Core `Table` objects, `Connection`s or handwritten SQL, apart from the
rule's named exceptions. It covers production code, scripts and tests.

`tests/unit/data/test_orm_only.py` reads every Python file under
`policyengine_api/`, `scripts/`, `tests/` and `.github/`. It doesn't read
`migrations/`, which the rule's `migration-revision` exception names, or the
proof fixtures in `rules/fixtures/`. The checks are in
`tests/unit/data/orm_access_support.py`, a port of policyengine-sim-api's
checker for `sim.persistence.orm-only`. They check each file on its own,
through the file's own imports of `sqlalchemy` and `sqlmodel`: SQLModel
re-exports SQLAlchemy's names, so `from sqlmodel import text` counts as
SQLAlchemy's `text`. They report four kinds of finding:

- **Core table declaration**: `Table(...)`, `Column(...)`, `table(...)`,
  `column(...)` and their clause classes, and `MetaData(...)` outside a
  declarative-base module.
- **Core table access**: a table read from a mapped class, a mapper or a
  `MetaData` (`__table__`, `local_table`, `metadata.tables`, a column's
  `.table`), and an annotation naming `Table` or `TableClause`.
- **Core engine or connection**: importing `Engine`, `create_engine` or
  `Connection` outside a session-factory module; opening a Connection there
  (`connect()`, `connection()`, `get_bind()`, or `begin()` on an engine);
  opening a database driver's connection there (a call into `psycopg`,
  `psycopg2`, `pymysql`, `sqlite3` or `mysql.connector` whose last name is
  `connect` or `Connect`, or ends with `Connection`, as in
  `psycopg.connect(url)`, `sqlite3.Connection(':memory:')` or
  `psycopg2.extras.RealDictConnection(dsn)`; naming a connection class
  without calling it isn't reported);
  `raw_connection()` in any module; `execute()` on anything not named as a session, and `scalar()`,
  `scalars()`, `stream()` or `stream_scalars()` on a name such as
  `connection`; listening for pool, engine or dialect events (`connect`,
  `checkout`, `before_cursor_execute`, `handle_error` and the rest) outside a
  session-factory module; and a public function of a session-factory module
  that returns an `Engine` or `Connection`.
- **raw SQL**: `text()`, `literal_column()`, `DDL()`, `exec_driver_sql()` and
  `cursor()`, apart from `text()` given as a server default, a partial
  index's condition or a check constraint's condition.

`connection()`, `get_bind()` and a driver's connection are reported in every
module outside the session-factory modules, whatever the module imports, and
`raw_connection()` and `exec_driver_sql()` in every module, session-factory
modules included. The names other libraries share, such as `execute()`,
`connect()`, `begin()` and `cursor()`, count only in a module that imports
`sqlalchemy` or `sqlmodel`. A statement run outside a session is reported with its constant
arguments, as `sqlite_connection.execute('PRAGMA foreign_keys = ON')`, and
every finding records the innermost class or function whose body holds it,
such as `Reconciler.apply`.

`test_every_table_is_mapped_by_a_class` imports `policyengine_api.data` and
the test modules that write rows, and reports every table they hold that no
mapped class maps, including tables built in ways the source checks can't see.

Two kinds of module have a role of their own:

- **Session-factory modules** are the only modules that may create or hold an
  Engine, open a Connection or a database driver's connection, or attach pool
  events:
  - `policyengine_api/data/orm.py`, API v1's runtime factory, with
    `policyengine_api/data/orm_pool_events.py`, whose listeners record the v1
    pool's events;
  - `policyengine_api/data/v1_sessions.py`, API v1's Session factories for
    commands that run once. Unlike `orm.py`, importing it loads no `.env`
    file, Cloud SQL connector or pool listeners;
  - `policyengine_api/data/v2/database.py`;
  - `tests/fixtures/database_sessions.py` for the tests;
  - `tests/unit/data/test_orm_pool_events.py`, whose tests drive the pool
    `orm_pool_events.py` listens to (they invalidate, detach and recycle
    connections and hold two at once, which no Session offers; their
    statements still run in Sessions), and
    `tests/unit/data/fake_driver_connections.py`, the fake database driver
    beneath those tests' engine, which opens its in-memory SQLite connections.

  They hand out Session factories, never an Engine or a Connection. When a module needs its own
  engine settings, such as `NullPool`, a deploy-time role or a separate URL,
  the session-factory module gets a function that returns a Session factory
  with them.
- **Declarative-base modules** are the only modules that may build
  `MetaData`: `policyengine_api/data/v1_models.py`,
  `policyengine_api/data/v2/models/__init__.py`, and
  `policyengine_api/data/v2/catalog/publication_staging_base.py`, the
  publication staging tables' own declarative base (SQLModel classes on a
  `registry()` of their own, so `api.v2.single-orm-layer` holds).

### Writing each kind of statement

- **Rows**: `session.add(Model(...))` and `session.add_all(...)`;
  `session.execute(insert(Model).values(...))`, including
  `sqlalchemy.dialects.postgresql.insert(Model).on_conflict_do_nothing(...)`;
  and `update(Model)`, `delete(Model)`, `select(Model)` and
  `select(Model.column)` in `session.execute` or `session.scalars`. A test
  helper such as `insert_row(connection, "table", **values)` becomes
  `add_row(session, Model, **values)`, given a mapped class. A JSON column
  takes the Python value, such as `[2026]`, not its JSON text.
- **Columns a mapper leaves out**: a column kept in its table but left out of
  the model's mapper (`exclude_properties`) until a revision drops it, as
  the per-user and cliff columns of `reports`, `report_runs` and
  `budget_window_runs` were until revision `4e30076d4b9f`, has no statement
  through the model: `update(Model).values(column=...)` raises
  `AttributeError`, a constructor value is never stored, and `Model.column`
  is the table's Core column, which the rule rules out even in a `select`. A
  test that sets or selects one maps it on a column-only class of a registry
  of its own, of the kind `tests.integration.privilege_statements` holds, and
  reads its declaration from SQLite's copy of the schema (`StoredTable.columns`
  in `tests.unit.v2.v2_schema_reading`) or from the database's `Inspector`.
- **Postgres functions**: `func`, as in
  `session.execute(select(func.current_database(), func.current_user()))`,
  `func.pg_backend_pid()` and `func.has_table_privilege(...)`.
- **Postgres settings**: `select(func.set_config(name, value, true()))` sets
  one until the transaction ends, as `SET LOCAL` does; read-only transactions
  use SQLAlchemy's `postgresql_readonly` option
  (`unpooled_v2_read_only_sessions`).
- **Schema reads**: SQLAlchemy's `Inspector`, which a function in a
  session-factory module returns for a Session factory or a Session. Never
  select from `information_schema` or `pg_catalog` with SQL text.
- **Roles in tests**: `act_as(session, role)` and `act_as_owner(session)` set
  the `role` setting with `set_config` inside the session's transaction, as
  `SET LOCAL ROLE role` and `SET LOCAL ROLE NONE` do. `NONE` acts as the user
  the session logged in as, the database's owner, even on a role's
  connection, where `RESET ROLE` would return to the role it started with. Or
  use a role's Session factory (`v2_sessions_as_role`), whose connections
  start as the role. Setup rows
  stay in the same rolled-back transaction where a test relies on that.
- **Refusals**: `refused(session, ...)` runs the statements inside it in
  `session.begin_nested()` and expects the error.
- **TRUNCATE in test cleanup**: `truncate(session, *models)` in the test
  session module (a named exception), or `delete(Model)` in dependency order
  where that is as simple.
- **COPY**: the publication staging tables are mapped classes on their own
  declarative base, not `V2_METADATA`, so Alembic never sees them. They stay
  `TEMPORARY` with `ON COMMIT DROP`. COPY through the driver connection stays
  the one driver-level exception, and the `INSERT ... SELECT` from the
  staging tables into the real tables uses `insert(Model).from_select(...)`.

### ORM-only exceptions

The rule's exceptions are its `[[rule.exception]]` entries in
`rules/registry.toml`, which the rule test reads. Each has a `path`, a
`category` and a `reason`:

- **`no-orm-form`**: one construct in one module that SQLAlchemy's ORM has no
  form for. `path` names the module, and `match` is the finding's source
  exactly as the check reports it, the text after its kind, such as
  `text(f'DROP ROLE {quoted_role}')`. `function` names the class or function
  whose body holds it, as the finding reports it after `in`, such as
  `apply_declared_privileges` or `Reconciler.apply`; `<module>` names a
  finding at module level, which the finding reports with no `in`. With
  `function`, the entry allows that source only there; without it, anywhere
  in the module. Every entry outside `tests/` gives its `function`. So does
  every entry whose `match` doesn't name one SQL statement, which would
  otherwise allow every such call in its module. A `match` names one
  statement only when it is a raw SQL construct (`text`, `TextClause`,
  `literal_column`, `DDL`) or a statement method (`execute`,
  `exec_driver_sql`, `scalar` and the like) whose first argument is a string
  or f-string whose literal text, less its SQL comments (`--` to the end of
  a line, and `/* ... */`), holds a statement keyword as a whole word, in any
  case: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `CREATE`,
  `DROP`, `ALTER`, `GRANT`, `REVOKE`, `EXPLAIN`, `ANALYZE`, `BEGIN`,
  `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `PRAGMA`, `SET`, `RESET`, `SHOW`,
  `WITH`, `COPY`, `LOCK`, `VACUUM`, `COMMENT`, `DO` or `CALL`, as
  `text(f'TRUNCATE {tables} CASCADE')` does. `text(statement)`,
  `text(f'{statement};')`, `text(f'{schema}.{table}')`,
  `text(f'{statement} -- cleanup')`, `literal_column('count(*)')`,
  `session.connection()`, `sqlite3.connect(':memory:')` and an attribute read
  name none. Two sites in
  different functions take an entry each. Only this rule's entries may give
  `function`: the rules loader refuses it on any other rule's.
- **`migration-revision`**: a path pattern the rule test doesn't read. It
  takes no `match` and no `function`.

The rule test fails on a finding no entry names, on an entry that names no
finding, and on an entry with an unknown category, a `no-orm-form` entry
without a `match`, an existing file or a `function` it needs, or a
`migration-revision` entry that names no file or gives a `match` or
`function`. Only statements SQLAlchemy can't express get an entry: `GRANT`
and `REVOKE`, `ALTER DEFAULT PRIVILEGES`, `CREATE`, `ALTER` and `DROP ROLE`
(with `DROP OWNED BY`), `CREATE VIEW` and `CREATE MATERIALIZED VIEW`, `DROP
TABLE`, `TRUNCATE`, `COPY`, `EXPLAIN`, `ANALYZE`, Alembic's need for a
Connection, and connection settings no SQL function sets, such as SQLite's
`foreign_keys` and `BEGIN IMMEDIATE`. Roles and Postgres settings inside a
transaction need none: `set_config` sets them. Keep the entries in as few
modules as possible. The entries:

1. **Alembic environments and revisions** (`migration-revision`),
   `migrations/**/*.py`. The environments run Alembic's migration context on
   a Connection, and the revisions are where schema changes belong
   (`api.data.sqlalchemy-and-alembic-only`), so the rule test doesn't read
   them.
2. **The rule's own check for unmapped tables** (`no-orm-form`, two
   entries), in `tests/unit/data/orm_access_support.py`'s
   `_unmapped_findings`: it reads which table each mapped class maps
   (`mapper.local_table`) and the tables a declarative base's metadata holds
   (`class_registry.metadata.tables`). It runs no statement.
3. **The tests' statements with no ORM form** (`no-orm-form`, nine entries),
   in `tests/fixtures/database_sessions.py`: SQLite's `PRAGMA foreign_keys`
   on each new in-memory connection; `BEGIN IMMEDIATE` on the concurrency
   test's SQLite file; `TRUNCATE ... CASCADE` for cleanup; `DROP TABLE`, so a
   route's catalog query fails with the database's own error and the MySQL
   lifecycle test finds a revision's table missing; `EXPLAIN`, to read the
   plan of an ORM statement (`query_plan` sends it with `exec_driver_sql`,
   because `text()` reads only `:name` parameters and the psycopg dialect
   writes `%(name)s::TYPE`); and `CREATE ROLE`, `DROP OWNED BY`, `DROP ROLE`
   and `GRANT` for the privilege tests' temporary roles.
4. **Catalog publication** (`no-orm-form`, four entries).
   `publication_staging.py` takes the Connection the publishing Session holds
   (`session.connection()`) in `create_staging_tables`, to create the
   `TEMPORARY` staging tables with `MetaData.create_all`, and in `copy_rows`,
   to stream rows with `COPY ... FROM STDIN` on a cursor of the psycopg
   connection beneath it (`driver_connection.cursor()`).
   `publication_statistics.py`'s `analyze_catalog_tables` runs one `ANALYZE`
   of the catalog tables a publication wrote, after it commits.
5. **Privilege reconciliation** (`no-orm-form`, two entries), in
   `privilege_reconciliation.py`: `CREATE ROLE ... NOLOGIN` for missing
   managed roles in `create_missing_roles`, only in the disposable test
   database, and, in `apply_declared_privileges`, the `GRANT` and `REVOKE`
   statements `privilege_plans` builds, with identifiers checked by
   `safe_identifier` and quoted by the session's dialect.
6. **Alembic's Connection** (`no-orm-form`, four entries). Alembic's
   `MigrationContext`, `compare_metadata` and `command.upgrade` take a
   Connection, so `pending_revisions.py`'s `v2_revision_is_pending` (the
   migration qualification commands' pending-revision check) and
   `scripts/v1_database_migration.py`'s `_config`, `database_state` and
   `metadata_differences` give them the Connection their Session holds,
   inside its transaction.
7. **The dialect's name** (`no-orm-form`), in
   `services/v2/user_types/database_connectors/reads.py`'s
   `acquire_user_type_change_lock`: `session.get_bind()` reads it to skip
   PostgreSQL's advisory lock on the SQLite test databases. It runs no
   statement on the engine.
8. **The privilege reconciliation tests' objects** (`no-orm-form`, three
   entries), in `tests/integration/catalog_privilege_objects.py`: `GRANT` on
   a schema or a sequence in `grant_on_schema_object`, which the shared
   `grant` (tables, views and materialized views) doesn't cover; `ALTER
   DEFAULT PRIVILEGES` in `alter_default_privileges`, for a default ACL; and
   `CREATE VIEW` and `CREATE MATERIALIZED VIEW` in `create_view`, which
   SQLAlchemy has no construct for. The reconciliation's catalog reads are
   tested on those grants.

A new exception is a rule change: add a `[[rule.exception]]` entry to the rule
in `rules/registry.toml`, explain here why the ORM can't express the
statement, and get it reviewed as one. `rules/` is code-owned
(`api.process.rule-machinery-code-owned`).

## API v1 database targets

Alembic manages the API v1 MySQL schema only. The local SQLite database is a
temporary application cache and is deliberately outside Alembic's lifecycle.
Every Alembic command must therefore receive an explicit MySQL URL:

```bash
export ALEMBIC_DATABASE_URL="mysql+pymysql://..."
uv run alembic -c alembic-v1.ini upgrade head
```

The v1 configuration is `alembic-v1.ini`; its revision tree is `migrations/v1`.
Do not put a database URL in the configuration. Keeping it without a default
prevents an omitted environment variable from silently migrating the wrong
database.

## Separate v1 and v2 migration domains

The two migration domains are mechanically independent:

| Domain | Configuration | Revisions | Database | Target metadata |
| --- | --- | --- | --- | --- |
| API v1 | `alembic-v1.ini` | `migrations/v1` | Cloud SQL MySQL | existing v1 declarative metadata |
| API v2-alpha | `alembic-v2.ini` | `migrations/v2` | Supabase Postgres | reviewed `SQLModel.metadata` only |

Never point `alembic-v1.ini` at Supabase, point `alembic-v2.ini` at Cloud SQL,
append v2 revisions under `migrations/v1`, import v1 metadata into the v2
environment, or use both Alembic and Supabase CLI schema migrations as
authorities for the same application tables.

## API v2-alpha database targets

This is the isolated Supabase/Postgres migration domain with a separate revision chain;
it is never a v1 Cloud SQL target.

Every v2 command requires an explicit, secret-supplied migration URL using a
Postgres dialect and the Psycopg 3 driver, for example
`postgresql+psycopg://...`. The v2 environment must not read
`ALEMBIC_DATABASE_URL`, infer a URL from v1 or runtime settings, select SQLite
under `FLASK_DEBUG`, or fall back to local Postgres. Missing, MySQL, SQLite, or
otherwise non-Postgres targets fail before any migration operation and without
printing the URL.

A command against a persistent Supabase environment must also verify its
declared environment and project reference against the approved target
configuration. Deployment obtains both non-secret values from controlled
GitHub Environment variables; local administrative commands must obtain and
supply the same values from the approved operator inventory. Concrete target
identifiers must not be committed as defaults or application target maps.
Before baseline generation or the first upgrade, it must require a successful
freshness qualification proving that the target contains no application
tables, Alembic history, or predecessor data. Missing, mismatched, ambiguous,
or non-fresh qualification stops the command; never drop, reset, reconcile,
adopt, or stamp the target automatically.

The sole exception is the completed pre-activation v2 baseline compaction. The
dedicated v2 target was still dormant, its complete row audit found only the
two known synthetic validation rows, and a recoverable ignored backup was
created. The old v2 chain then downgraded its own application schema to
`base` before any old revision file was removed. A new parentless baseline was
autogenerated from the complete current SQLModel metadata and qualified before
being applied. This is not permission to rewrite later applied history: never
repeat it once v2 contains retained domain data or serves production traffic,
never stamp across a compaction, and never apply it to v1 or Supabase-managed
schemas and Storage.

Only a separate, explicit disposable-test mode may omit Supabase identity. It
is limited to an isolated Postgres database created for local or CI migration
lifecycle tests and must be rejected for staging, production, or any other
persistent target.

The v2 environment imports the controlled v2 table-model package before
exposing `SQLModel.metadata`. That metadata is the authoritative application
table set; do not maintain a second exact table-name allowlist. Targeted
validation must reject known v1-only names, `runtime_bundles`, and standalone
population tables. Review every autogenerated table change, and compare the
live schema directly with the complete SQLModel metadata during the migration
lifecycle.

## Table privileges

The table privileges of the managed v2 database roles are declared in
`policyengine_api/data/v2/privileges.py`, not in Alembic revisions: revisions
stay generated-only, the simulation API's role name differs per environment,
and a revision runs once per database, so it can't repair drift.

| Role | Used by |
| --- | --- |
| `policyengine_v2_runtime` | The Public API on Cloud Run |
| `policyengine_v2_catalog_writer` | `scripts/publish_v2_metadata_catalog.py`, which also runs `ANALYZE` on seven catalog tables after every publication, with `MAINTAIN` (PostgreSQL 17) |
| `policyengine_stage12_<environment>` | The simulation API and its Modal worker, on the temporary comparison-run tables |
| `policyengine_v2_simulation_service` | The simulation API on Cloud Run: creates simulations, reports, their runs, budget-window runs, household jobs and simulation runs' cliff calculations, and reads the policy, dynamic, household and catalog rows a run needs. It updates only the status, Modal call ID, error and completion columns of the runs, household jobs and cliff calculations whose Modal calls it starts, and the status, error and completion columns of a budget-window run, which it fails at once when Modal refuses the calls of the window's first years |
| `policyengine_v2_modal_worker` | The simulation API's Modal workers: write their runs', household jobs' and cliff calculations' status and results, and budget-window runs' status, and read the rows a run needs. It updates only a run's or cliff calculation's status, Modal call ID, error, time and result columns, and a budget-window run's status, error and time columns: each year's coordinator starts the window's next unstarted year when its own year finishes, the last year to finish marks the window succeeded, and a failed year fails it. The workers' code, not the database, keeps a worker to its own run |

Every v2 table has an entry for every role, so "no access" is a decision, not
an omission. A privilege is declared on the whole table, or with
`update_columns(...)` on only the columns it names; PostgreSQL then refuses a
statement that sets any other column, so neither simulation API role can
change what a run is. A role never holds both kinds of `UPDATE` on one table:
the whole-table one would let it set every column. The migration role owns every table and isn't listed. Three rules
check the declarations:

- `api.v2.runtime-privileges-declared`: a unit test reads each connector
  module and fails when it needs a privilege its role isn't declared to hold.
- `api.v2.runtime-privileges-tested-as-runtime-role`: the cross-database
  integration tests run the v2 user services and the parameter tree read as
  `policyengine_v2_runtime`, catalog publication as
  `policyengine_v2_catalog_writer`, and the comparison-run services as
  `policyengine_stage12_test`, holding only their declared privileges.
  `tests/integration/test_v2_simulation_role_privileges.py` runs the
  simulation API's writes as its two roles; their code lives in the simulation
  API's repository. `tests/integration/test_v2_household_calculation_reads.py`
  reads the household jobs they write through the household calculation
  service as `policyengine_v2_runtime`.
- `api.v2.deployed-privileges-match`: every deploy runs
  `scripts/reconcile_v2_privileges.py apply` right after the schema upgrade,
  then `verify`, before the catalog is seeded.

`apply` grants each declared privilege a role lacks, as one `GRANT` per role
and table and one per column privilege. It revokes one kind of privilege
only: one a role holds directly on a whole table that the file declares for
named columns only. The projects' default privileges give the runtime role
`UPDATE` on every new table, so `user_type_changes`, where it may update only
`dismissed_at`, starts with one. PostgreSQL's `REVOKE` on a table also removes
the role's column grants of that privilege, undeclared ones included, so
`apply` grants the declared columns again, in the same transaction; the job
summary lists the revoke with the undeclared column grants it removed. It
reports every other privilege the file doesn't declare, on whole tables or on
columns, and the projects' default privileges, without revoking them. It
changes nothing when a declared role or table is missing. `verify` checks each
column of a column privilege with `has_column_privilege`, and fails when a role
still holds the same privilege on the whole table: through a role it belongs
to, or through a grant another role made, which the owner's `REVOKE` leaves in
place. The roles themselves are provisioned outside the repository;
`--create-missing-roles` is accepted only for the disposable test database,
which has no default privileges.

A pull request may declare a role before an operator creates it by listing it
in `ROLES_AWAITING_PROVISIONING` in `privileges.py`. While a listed role is
missing, `apply` and `verify` skip it and name it in their output and the job
summary instead of failing; once it exists, the next deploy grants and checks
its privileges. Remove the role from the set once it exists in staging and
production, so that its absence fails the deploy again.

The declarations include write privileges for code paths production doesn't
turn on: the dual-write copies into `legacy_policy_mappings` and
`legacy_household_mappings`, and the writes behind the native `/v2/policies`,
`/v2/dynamics` and `/v2/households` routes. Narrow them when those tables are
removed.

When a pull request adds or changes a v2 table, or a connector's use of one:

1. Update the table's entry in `privileges.py` for every role.
2. Run `make test`, which includes `tests/unit/v2/test_privilege_manifest.py`.
3. Run the integration tests as the managed roles against disposable
   PostgreSQL:

   ```bash
   export V2_MIGRATION_DATABASE_URL="postgresql+psycopg://.../policyengine_v2_alembic_test" \
     V2_ALEMBIC_DISPOSABLE_TEST=1 DEPLOYMENT_ENVIRONMENT=test
   uv run alembic -c alembic-v2.ini upgrade head
   uv run python scripts/reconcile_v2_privileges.py apply --create-missing-roles
   uv run python scripts/reconcile_v2_privileges.py verify
   uv run pytest -q tests/integration/test_v2_user_identity_persistence.py \
     tests/integration/test_v2_stage12_comparison_persistence.py \
     tests/integration/test_v2_metadata_routes.py \
     tests/integration/test_v2_catalog_publication.py \
     tests/integration/test_v2_catalog_publication_pruning.py \
     tests/integration/test_v2_simulation_role_privileges.py \
     tests/integration/test_v2_shared_report_rows.py \
     tests/integration/test_v2_household_calculation_reads.py \
     tests/integration/test_v2_privilege_reconciliation.py
   ```

Never grant privileges by hand in staging or production; they reach those
databases only through the deploy step, after review. The unit test reads

outside `database_connectors/`; the integration tests catch those.

## V2 application-data migrations

Alembic is also the sole authority for intentional migrations of retained v2
application data. Every such revision must originate from the same mandatory
autogeneration command used for schema revisions:

```bash
uv run alembic -c alembic-v2.ini revision --autogenerate -m "<description>"
```

Do not create a blank revision and add `bulk_insert`, SQL strings, ORM calls,
or other data operations by hand. A concrete data-migration requirement must
provide a reviewed generation source capable of producing deterministic and
reversible operations. If safe autogeneration is unavailable, invoke the human
decision rule above instead of maintaining speculative migration machinery.

The v2 baseline contains no reference-data operation, desired-state row
declaration, comparator, or synthetic validation row. Future retained-data
migrations still require a concrete reviewed generation source; do not add a
speculative general-purpose data-migration framework merely to exercise the
policy.

`alembic check` for v2 must detect schema drift.
Application startup, model import, project provisioning, and external
infrastructure provisioning must never call `create_all`
(`api.data.sqlalchemy-and-alembic-only`), create or stamp application tables,
or mutate versioned application data. The Supabase CLI is
not an application schema or seed migration authority.

Canonical metadata catalogs derived from the exact installed country and
`policyengine` packages are not hand-authored migration data. A later-stage,
explicit deployment seeder may materialize those package-derived rows after
`alembic upgrade head` when its reviewed contract requires transactional,
idempotent row-only behavior, recorded source package versions, and fail-closed
handling of partial catalogs. Such a seeder must perform no DDL, must not run at
application startup, and must not transform or delete retained domain data;
those operations remain Alembic migrations. Catalog pruning, below, is the one
exception.

Migration credentials remain separate from future runtime credentials. The
migration identity may create and alter the v2 application schema; the runtime
identity must not. Neither credential nor a secret-bearing URL belongs in an
Alembic INI file, log, committed environment file, generated artifact, or
revision.

### Catalog pruning: the seeder's one deletion

Catalog publication (`scripts/publish_v2_metadata_catalog.py`, run by the
release workflow's seed jobs as `policyengine_v2_catalog_writer`) deletes
package-derived rows of older catalog versions. Each stored version costs
about 550 MB per environment, mostly its current-law parameter values. The
code is `policyengine_api/data/v2/catalog/publication_pruning.py`, called
from `publish_catalog` in `publication.py`.

Every publication sets `tax_benefit_model_versions.catalog_last_published_at`
for each version it publishes, new, unchanged or restored, in its
transaction. After the publication transaction commits, publication keeps,
for each country's model, the version it published or republished (the
installed one) and the two most recently published other stored versions
(by `catalog_last_published_at`, or `created_at` where that is null, then
`created_at` and version text). Two are kept because the release workflow
seeds before it deploys and puts the previous revision back when promotion
fails: after one failed promotion, or a rollback to an older version, the
version still serving is one of them. Two consecutive failed promotions
followed by a third release can still prune the serving version. The rule
is decided in one function, `catalog_versions_to_prune`.

It chooses every other stored version of that model whose
`catalog_values_pruned_at` is null, and prunes at most two of them per run
(`MAX_CATALOG_VERSIONS_PRUNED_PER_RUN`), the oldest created first; the
evidence counts the rest (`catalog_versions_left_to_prune`), which later
publications prune. For each, it runs one transaction that takes the
publication advisory lock, reads the model's stored versions again, skips the
version if the rule no longer chooses it, and otherwise deletes exactly:

- the version's current-law `parameter_values`: rows of the version's
  parameters whose `policy_id` and `dynamic_id` are both null;
- the version's `parameter_tree_children` rows;
- the version's `parameter_search_files` rows;

and sets the version's `catalog_values_pruned_at` to the current time. It
never deletes or changes any other row: not `parameters` (deleting one
cascades to every value of it, saved reforms' included), not the
`tax_benefit_model_versions` row apart from that column, and not
`parameter_nodes`, `variables`, `regions`, `datasets`, `policies`,
`dynamics` or any `parameter_values` row with a `policy_id` or `dynamic_id`.
A transaction that raises an exception, of any kind, rolls back that
version alone; the failure is reported in the command's evidence and on
stderr, the command still succeeds, and the next publication tries again.

The deleted rows are rebuilt from the packages, not lost: when publication
runs for a version whose `catalog_values_pruned_at` is set (a release that
installs it again), it inserts the version's current-law values from the
installed packages and clears the column inside the publication transaction,
before the usual exact comparison of the stored version, and writes the
version's parameter tree and search file as it does for a version that has
none. The rows it writes equal those a first publication of the version
writes, with the same value IDs. Until then the metadata routes that serve
the deleted rows answer 404 for that version, with `Cache-Control: no-store`,
or 503 when it is the version the serving revision runs.

The catalog writer holds `DELETE` on the three tables and `UPDATE` on
`tax_benefit_model_versions` for this (`privileges.py`). Pruning runs no DDL;
revision `334859ef4fec` added the nullable `catalog_last_published_at` and
`catalog_values_pruned_at` columns, autogenerated with no post-generation
corrections apart from `ruff format`.

Its downgrade drops both columns, and with them the record of which versions
are pruned: a pruned version then looks complete to the parent revision's code,
which serves it with no current-law values and fails the exact comparison if
it publishes that version, with nothing to restore it. Downgrading past the
revision is therefore safe only while no version is pruned (no
`tax_benefit_model_versions` row has `catalog_values_pruned_at` set).
From the head, such a downgrade first runs the later revisions' downgrades:
`d417fe8b1b17`'s drops `user_dynamics` with every saved dynamic (see "API v2
users' saved dynamics"),
`4e30076d4b9f`'s adds the dropped report columns back empty (see "API v2 report
column drops"),
`bc334f9877b7`'s drops `cliff_impacts` with every simulation run's cliff
results (see "API v2 simulation-run cliff impacts"),
`9d1d12a7ac58`'s needs `dynamics` empty (see "API v2 dynamics stored like
policies"),
`f519a77ba122`'s drops `user_invitations` and needs no recorded change with
source `invitation` (see "API v2 user invitations"),
`94dc43079186`'s drops every user's report-run record, the simulation and
report keys and the window runs' .py versions, and needs no report or report
run to exist, since `4e30076d4b9f`'s restored their labels and triggers empty
(see "API v2 shared reports and user report-run records"),
`970be5d29283`'s drops `user_type_changes` with every recorded change (see
"API v2 user type changes"), `617f531f1506`'s needs no user to be an author
or an admin (see "API v2 user types"), and `1356f658347d`'s needs
`simulations` empty (see "API v2 simulation runs").
Otherwise restore the versions the target code may install or serve first, by
publishing each with this revision's code, as the Stage 9 runbook's rollback
section describes. Production downgrades are never automatic in any case.

The rule that the serving revision must work with the database changed on
its own (see "CI/CD behavior") has one accepted exception here. During the
first release that includes pruning, the seed job prunes while the previous
revision, whose code doesn't read `catalog_values_pruned_at`, still serves.
Until that release is promoted, and until the next successful release if
promotion fails, the previous revision answers a request naming a pruned
version in `policyengine_version` on `/v2/parameter-values`,
`/v2/model-catalog/parameters` and `/v2/model-catalog/variables` with a 200
holding no current-law values, `Cache-Control: public, max-age=86400` and an
`ETag`. The maintainers accepted this for that one release, because nothing
in production calls these routes with an older version until the v3 switch.
Later releases' previous revisions read the column and answer 404 (503
before issue #4243). The Stage
9 runbook's "Pre-activation sequence" describes the window.

The maintainers' approval of this exception is the review of the pull request
that added it. Deleting from another table, deleting another kind of row, or
deleting rows that publication can't rebuild from the installed packages
needs the same human migration decision.

### CI/CD behavior

- Pull requests first detect whether the v1 Alembic surface changed. Relevant
  PRs invoke `.github/workflows/alembic-v1-check.yml`; unrelated PRs skip it.
- Every merge to `master` runs the reusable disposable-MySQL qualification next
  to lint, regardless of which paths changed. The release commit's run skips it
  only when `check-release-commit` confirms that the release commit changes
  nothing but release files and that the merge commit's run passed it
  (`.github/release_commit.py`); otherwise the release run runs it again.
- The release migration job runs before either staging deployment. It refuses
  unversioned or invalid history, takes a backup only when revisions are
  pending, upgrades under the advisory lock, and requires zero post-migration
  drift.
- In each environment the v1 release migration and the v2 seeding job
  (`seed-v2-database.yml`, which upgrades the v2 schema and publishes the
  catalog) run side by side: the v1 job connects only to Cloud SQL and the
  seeding job only to the v2 database. Each Cloud Run candidate deploy needs
  both, so a candidate is never built until both databases are upgraded. When
  one of them fails, the release stops with the other already applied; the
  serving revision must work with either database upgraded on its own.
- Database credentials and derived URLs must never be printed. The application
  runtime account must not be granted schema-migration privileges.
- Production downgrades are never automatic. MySQL DDL is non-transactional, so
  rollback means application compatibility plus a reviewed forward fix or a
  database restore.

### API v2 countries rows

Revision `fb1a3e40d3d6` was autogenerated after adding the `countries` table
and replacing the US-and-UK checks on `users.primary_country` and on the
`country_id` of households, policies and the four user association tables
with foreign keys to it. It contains one hand-written operation: it inserts
the `uk` and `us` rows, both household and society-wide capable, between the
generated table creation and the generated foreign keys, which otherwise fail
on any database whose rows already name either country. The rows are exactly
the values the replaced checks allowed. The generated downgrade removes them
with the table, and its restored checks fail if any record names another
country.

Inserting rows is a data operation, which this skill otherwise forbids. The
maintainers approved this insert as a one-off exception, because the new
foreign keys need the rows in the same revision. Unit tests pin the
operation, and the v2 Postgres lifecycle test covers an upgrade that keeps
existing rows, the downgrade, a downgrade refused by another country's
records, and the re-upgrade.

The table must list exactly the countries in
`policyengine_api/supported_countries.py`: the Public API refuses to start
when they differ (`policyengine_api/startup_country_check.py`). Listing
another country later needs a revision that inserts its row, and the same
human migration decision. The deploy runs that revision before it starts
the new release, so instances of the previous release that start afterwards,
and a rollback to it, refuse to start until the revision is downgraded. The
module docstring of `supported_countries.py` lists the other checks a new
country must widen.

### API v2 shared reports and user report-run records

Revision `94dc43079186` (parent `1e1e3f079f2c`) was autogenerated, with its
ID given by `--rev-id`, after these model changes, so that identical requests
share simulations, reports and runs. It was generated on `0c136a278f29`; when
`master` gained the withheld area codes revision `1e1e3f079f2c` on the same
parent, its `down_revision` moved to `1e1e3f079f2c`, and generating it again
from there gives the same operations.

- `simulations` and `reports` gain `key_version` and `definition_key`, and
  `reports` also `dataset_independent_key`: the simulation service's SHA-256
  of what the row calculates (and, for the report key shared across datasets,
  the same without the dataset), in the key format
  `key_version` names. They are nullable, so rows from before the keys stay
  unkeyed, and each table is unique on `(key_version, definition_key)`;
  PostgreSQL's unique constraint allows any number of unkeyed rows. Checks
  require a key of 64 lowercase hexadecimal digits, a positive `key_version`,
  and a key with its version (on `reports`, all three columns or none). An
  index on `dataset_independent_key` alone finds the reports that share that
  key, a national report and its local-area report: the app looks one up by
  the other's key, which holds its own key version.
- `simulation_runs` and `report_runs` gain `forced` (`false` by default, for
  every existing row and every writer that doesn't name it), which marks a run
  a forced re-run created.
- Partial unique indexes allow one run that hasn't failed and isn't forced per
  definition and version set:
  `uq_simulation_runs_unfailed_unforced_versions` on `(simulation_id, year,
  tax_benefit_model_version_id, country_package_version,

  `(report_id, country_package_version, policyengine_version)` outside budget

  next request starts a new run, and a forced re-run is an extra run nothing
  joins. The simulation service finds or creates with `INSERT ... ON
  CONFLICT (<the index's columns>) WHERE <its condition> DO NOTHING`, naming
  each index's whole condition: `status <> 'failed' AND NOT forced` for
  simulation runs, and `budget_window_run_id IS NULL AND status <> 'failed'

  index. Naming a conflict target needs `SELECT` as well as `INSERT` on the

  for SQLite, so the unit tests' databases keep the same rule. A failed run
  can't be set back to another status while a newer unfailed run on its
  versions exists.
- `budget_window_runs` gains `policyengine_version` (nullable: window runs
  written before it stay unversioned, and an unversioned run is never
  joined), and `uq_budget_window_runs_unfailed_unforced_versions` allows one
  window run per report, catalog version and `policyengine_version` that
  hasn't failed and isn't recalculated (`status <> 'failed' AND NOT
  recalculate`): `recalculate` is a window run's forced marker. Each year's
  report run belongs to its window run, outside the report-run index; each
  year's simulation runs are under the simulation-run index.
- The per-user columns of shared rows become nullable, with no default:
  `reports.label`, `report_runs.trigger` and `budget_window_runs.trigger`
  (`reports.description` and `user_id` already were). A shared row describes
  no one caller, so the simulation service stops writing them, API v1's models
  leave them out, and a later revision drops them. A user's trigger is on
  their `user_report_run_associations` row.
- `user_report_run_associations` records each user's request for a report
  run: the user (`CASCADE`), the run (`RESTRICT`, so a run a user asked for
  can't be deleted), `requested_at` (required, with no default: the writer
  says when the user asked) and `trigger` (`initial` for a create, `manual`
  for a re-run; checked, since a system re-run is nobody's request). One row
  per user and run. The runtime role may read, insert and delete its rows,
  never update them, and no other role reads them.

One post-generation correction: `user_report_run_associations.trigger`
reuses the `v2_report_run_trigger` type (`create_type=False`) instead of
creating it again, as `1356f658347d` does for `budget_window_runs`.

The previous Public API revision maps none of the new columns or the new

  succeeded or failed row has `completed_at`
  (`ck_cliff_impacts_finished_completion`).
- The result: `cliff_gap`, the weighted total of the net income people would
  lose from a small rise in their earnings, and `cliff_share`, the weighted
  number of people on a cliff divided by the weighted number of adults, both
  double precision. A succeeded row has both, and no other row has either
  (`ck_cliff_impacts_result_when_succeeded`). Neither is range-checked: .py
  doesn't keep the share to at most 1, and a filtered simulation with no
  adults gives NaN.
- `uq_cliff_impacts_unfailed`, a partial unique index on `simulation_run_id`
  where `status <> 'failed'` (also declared for SQLite): a run has at most one
  calculation that hasn't failed, and so at most one result. The simulation
  service is to start one with `INSERT ... ON CONFLICT (simulation_run_id)
  WHERE status <> 'failed' DO NOTHING`, so that two requests at once start
  one calculation and the second joins it. A failed calculation never counts:
  it stays as a record, and the next request inserts another.
- An index on `(status, started_at)`, as `simulation_runs` has, for finding
  unfinished calculations by age, as the simulation API's stuck-run sweep
  does for runs: a calculation whose worker ended without recording its
  outcome stays unfinished, and keeps later requests from starting another,
  until something fails it.

A result has no versions of its own: it inherits its run's catalog and
package versions, so it is calculated only for a run on the versions the
simulation API serves. The simulation service may read and insert rows and update their
status, Modal call ID, error and completion columns; the Modal worker may read
them and update their state and result columns, never insert them; the
runtime role may read them; neither simulation role may change the run a row
names or delete a row. The reconcile step after each schema upgrade grants
them. Until the simulation API writes the table, no run has a cliff
calculation, and its cliffs stay refused. Revision `4e30076d4b9f` drops
`report_runs`' four cliff columns.

It has one post-generation correction, commented in the revision: `status`
reuses the baseline's `v2_simulation_status` type
(`postgresql.ENUM(..., create_type=False)`), as `1356f658347d` does for
`simulation_runs.status`; the generated `create_table` would create the type
again and fail. So the downgrade, which drops only the table, leaves the type
to `simulation_runs`.

The revision writes no data and changes no other table, and API v1's
previous release, which doesn't map the table, keeps working at it. The
downgrade drops the table with every calculation and result; a later
calculation of the same runs on the same versions gives the same numbers.
`tests/integration/test_alembic_v2_cliff_impacts.py` checks that nothing
else changes, that the downgrade leaves the type and an upgrade works again,
and the index, checks and delete rule;
`tests/integration/test_v2_simulation_role_privileges.py` runs the writes
and reads as the roles that do them.

### API v2 report column drops

Revision `4e30076d4b9f` (parent `bc334f9877b7`) was autogenerated, with its ID
given by `--rev-id`, after these columns left the models. Reports, report runs
and budget-window runs are shared by every request that joins them, so they
hold nothing about one caller, and a report run's cliffs are its two simulation
runs' results in `cliff_impacts`. It drops:

- `reports.label`, `description` and `user_id`, with
  `fk_reports_user_id_users` and `ix_reports_user_id`. A report's name and
  description are on each user's saved report, and deleting a user no longer
  touches `reports`.
- `report_runs.trigger` and `budget_window_runs.trigger`. Each user's trigger
  is on their `user_report_run_associations` row, which still uses the
  `v2_report_run_trigger` type, and `/v2/reports` run items no longer have a
  `trigger` field.
- `report_runs`' `baseline_cliff_gap`, `baseline_cliff_share`,
  `reform_cliff_gap` and `reform_cliff_share`, with
  `ck_report_runs_cliff_impact_complete`. The Modal worker's column privileges
  on them go too.

It has one post-generation correction, commented in the revision: autogenerate
strips the first and last parenthesis of the reflected check condition, which
leaves the downgrade's `create_check_constraint` with invalid SQL.

**What must be in production first.** The deploy upgrades the schema before the
new Cloud Run revision takes traffic (see "CI/CD behavior"), so the previous
release serves on this schema, for longer if promotion fails:

- An API v1 release whose `Report`, `ReportRun` and `BudgetWindowRun` no longer
  map these columns. Report reads load whole rows, and a whole-row load names
  every mapped column, so otherwise every `/v2/reports` read fails.
- A simulation API release whose v2 Modal runtime no longer writes the four
  cliff columns. Otherwise every economy report run's completion fails.

The simulation API's table models must then lose the same columns. Until they
do, its comparison with API v1's tables fails; requests are not affected.

**The dropped values are not kept.** Nothing copies them, since these rows name
no user to copy them to, and the downgrade can't restore them. One merge takes
the revision through staging and production in a single release run, so before
merging, an operator exports what those rows hold in both environments with
these read-only queries, and keeps the result outside the repository, because
labels and descriptions are users' text:

```sql
SELECT id, created_at, label, description, user_id FROM reports
WHERE label IS NOT NULL OR description IS NOT NULL OR user_id IS NOT NULL;
SELECT id, report_id, created_at, trigger, baseline_cliff_gap,
       baseline_cliff_share, reform_cliff_gap, reform_cliff_share
FROM report_runs
WHERE trigger IS NOT NULL OR baseline_cliff_gap IS NOT NULL;
SELECT id, report_id, created_at, trigger FROM budget_window_runs
WHERE trigger IS NOT NULL;
```

The downgrade adds the columns, key, index and check back with every value
null. The Modal worker's `UPDATE` on the four cliff columns doesn't come back
with them: it returns only when `reconcile_v2_privileges.py apply` runs from a
`privileges.py` that names them. Continuing below `bc334f9877b7` to
`94dc43079186`'s parent fails while any report or run exists, because that
downgrade needs every report to have a label and every run a trigger.

`tests/integration/test_alembic_v2_report_column_drops.py` compares the revision
and its downgrade with the parent schema built from the base, and checks that
rows survive the upgrade, that the downgrade restores no values, and that the
deploy's privilege steps pass.

### API v2 users' saved dynamics

Revision `d417fe8b1b17` (parent `4e30076d4b9f`) was autogenerated, with no
post-generation corrections apart from `ruff format`, after the model gained
`UserDynamic`. Its ID was chosen with `--rev-id`, so the tests written before it
could name it. It was generated on `9d1d12a7ac58`; when `master` gained the
cliff impacts and report column drops revisions, its `down_revision` moved to
`4e30076d4b9f`, and generating it again from there gives the same operations.
It creates `user_dynamics`, users' named saved dynamics, built
like `user_policies` without its v1 reference, `baseline` and `provenance`:

- `user_id`, a key to `users`, `CASCADE`, indexed: a user's saved dynamics
  are deleted with the user, and the sign-in merge moves a browser's to the
  account it signs in to.
- `country_id`, a key to `countries`, `RESTRICT`.
- `dynamic_id` (required): with `country_id`, a key to `dynamics (id,
  country_id)` (`fk_user_dynamics_dynamic_country`, `RESTRICT`). A saved
  dynamic names a dynamic of its own country, and a dynamic that users have
  saved can't be deleted.
- `name` (255) and `description` (text), both nullable.
- `(id, country_id)` is unique (`uq_user_dynamics_id_country`), so other
  tables can name a saved dynamic of one country. There is no unique rule on
  the owner and dynamic: a user may save one dynamic more than once.
- Indexes on `(country_id, user_id, created_at, id)` for a user's listing,
  and on `(country_id, dynamic_id)`, which also serves the key's check when a
  dynamic is deleted.

`user_dynamics` has no v1 column, since v1 has no dynamics. API v1 no longer
writes v1 saved policies (their routes were removed on 2026-10-22), so no
copy creates saved dynamics. D4 · 1's migration gives each v1 saved policy that
holds assumption values a saved dynamic with its name, through
`services.v2.user_dynamics.services.create_user_dynamic_in_session`.

The runtime role reads and writes `user_dynamics`, as it does `user_policies`;
no other role has access. The previous API v1 revision doesn't map the table,
so it keeps working at this revision, and deleting a user through it still
deletes their saved dynamics, through the key's `CASCADE`. Its sign-in merge
doesn't move saved dynamics, though: while it serves after a rollback, a
browser that signs in to an existing account loses its saved dynamics with
its unauthenticated user. The downgrade drops the table with every saved
dynamic, and the dynamics they named stay.
`tests/integration/test_alembic_v2_user_dynamics.py` checks that nothing else
changes, the keys, deletion with the user and the downgrade.
