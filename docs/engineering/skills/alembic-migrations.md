# Alembic Migrations

Use this skill whenever adding or changing SQLAlchemy models, Alembic
configuration, database schema, migration revisions, or code that connects to
a database.

## Mandatory generation rule

AI **MUST NOT manually author Alembic revision scripts**. Generate every schema
revision from reviewed SQLAlchemy metadata:

```bash
# API v1 / Cloud SQL MySQL
uv run alembic -c alembic-v1.ini revision --autogenerate -m "<description>"

# API v2-alpha / Supabase Postgres
uv run alembic -c alembic-v2.ini revision --autogenerate -m "<description>"
```

The mandatory generation operation is `alembic revision --autogenerate`.
Always select the configuration for the intended migration domain explicitly;
never use Alembic's default configuration discovery. The v1 configuration
keeps MySQL revisions in `migrations/v1`, while the v2 configuration keeps
Postgres revisions in `migrations/v2`.

If generated operations are wrong, first correct the model metadata and
regenerate. AI may make minimal post-generation corrections only for dialect compatibility,
reversibility, or an objectively incorrect autogenerated
operation. Document each correction and cover it with upgrade and downgrade
tests. Do not add arbitrary schema or data operations to a generated revision.

If the required migration cannot be expressed safely by autogeneration plus
those narrow review corrections, stop and request a human migration decision.

## Required checks

Before committing a migration, run these checks against the matching domain:

1. Run `uv run alembic -c <configuration> check` and review the generated
   schema operations.
2. Upgrade a fresh database to `head`.
3. Compare the database to the complete ORM metadata before release.
4. Downgrade one revision and upgrade to `head` again in an isolated database.
5. Confirm application startup performs no implicit DDL
   (`api.data.sqlalchemy-and-alembic-only` checks the code for it; see the
   next section).

Never print database credentials or embed them in Alembic configuration. The
deployed v1 database is already versioned; never recreate or restamp its
baseline. Missing or invalid revision history must fail closed for manual
recovery.

## Database access through SQLAlchemy and Alembic

Rule `api.data.sqlalchemy-and-alembic-only`: code connects to relational
databases only through SQLAlchemy engines, connections and sessions, never by
calling a database driver directly, and changes persistent schema only through
Alembic revisions.

- API v1 builds its Cloud SQL engine in `policyengine_api/data/orm.py`. The
  Cloud SQL connector is passed to `create_engine` as `creator=`, so SQLAlchemy
  opens and pools the connections. SQLAlchemy does not add its MySQL connection
  arguments to connections a `creator=` function opens, so the connector call
  passes MySQL's `CLIENT_FOUND_ROWS` flag in `client_flag` itself; with it an
  UPDATE reports the rows it matched rather than the rows whose values changed,
  which SQLAlchemy needs to check UPDATE row counts.
- API v2 builds its SQLModel engine from a `postgresql+psycopg` URL in
  `policyengine_api/data/v2/database.py`.
- Take connections and sessions from those engines, never from
  `psycopg.connect`, `pymysql.connect`, `sqlite3.connect` or another driver.
- Change schema only with an autogenerated revision (see "Mandatory generation
  rule"). Application code, scripts and CI never call `create_all`,
  `drop_all`, `Table.create` or `Table.drop`, build SQLAlchemy DDL constructs,
  call Alembic operations outside `migrations/`, or run `CREATE`, `ALTER`,
  `DROP` or `TRUNCATE` SQL.

`tests/unit/data/test_database_access_boundaries.py` checks `policyengine_api/`,
`scripts/`, `migrations/` and `.github/`, skipping tests and the paths the
rule's `migration-revision` exception names: the generated revisions under
`migrations/*/versions/`. It parses each module and reports:

- imports of `psycopg`, `psycopg2`, `pymysql`, `MySQLdb`, `mysql.connector`,
  `sqlite3`, `asyncpg`, `pg8000`, `aiosqlite` or `aiomysql`, including through
  `importlib.import_module`;
- access to the driver connection beneath SQLAlchemy: the `driver_connection`
  and `dbapi_connection` attributes and `raw_connection()`, and a driver
  connection's private attributes (pymysql's socket, `_sock`), read as an
  attribute or through `getattr`;
- `create_all()`, `drop_all()`, and `create()` or `drop()` on a table, index
  or sequence; SQLAlchemy DDL constructs such as `CreateTable`; and `op.*`
  calls or `alembic.op` imports outside `migrations/`;
- string literals, other than docstrings, that begin a `CREATE`, `ALTER` or
  `DROP` of a table, type, schema, database, index, sequence, view or
  extension, or a `TRUNCATE`.

### Declared exceptions

The rule's exceptions are its `[[rule.exception]]` entries in
`rules/registry.toml`, which the check reads. Each has a `path`, a `category`
and a `reason`:

- **`driver-access`** and **`schema-change`**: one construct in one file. The
  entry's `path` names the file and its `match` names the construct, exactly
  as the check reports it, such as `import psycopg.sql` or
  `call STAGING_METADATA.create_all()`.
- **`migration-revision`**: a path pattern the check doesn't scan at all.

The check fails on a construct no entry allows, on an entry with an unknown
category or a missing `match`, and on an entry that no longer matches anything,
so an exception can't gain a name or a file, and is removed once it's unused.
The entries:

1. **COPY through the driver connection** (`driver-access`, three entries).
   Publication writes rows with Postgres `COPY ... FROM STDIN`, which
   SQLAlchemy has no API for. `copy_rows` in
   `policyengine_api/data/v2/catalog/publication_staging.py` uses the psycopg
   connection beneath a SQLAlchemy `Connection`
   (`connection.connection.driver_connection`) that SQLAlchemy opened and still
   manages, so the transaction stays SQLAlchemy's. It imports `psycopg.sql` to
   compose the `COPY` statement and `psycopg.types.json.Jsonb` to send JSON
   values.
2. **Temporary staging tables** (`schema-change`). `create_staging_tables` in
   the same module calls `STAGING_METADATA.create_all` for tables declared
   `TEMPORARY` with `ON COMMIT DROP`. Postgres drops them when the publishing
   transaction commits, so they are not persistent schema. The check confirms
   that every table on `STAGING_METADATA` compiles to
   `CREATE TEMPORARY TABLE ... ON COMMIT DROP`.
3. **The v1 pool's socket diagnostics** (`driver-access`). The listeners in
   `policyengine_api/data/orm_pool_events.py` that record the v1 Cloud SQL
   pool's connects, invalidations and closes read the file descriptor and
   local port of pymysql's socket, `getattr(connection, "_sock", None)`, from
   the driver connection SQLAlchemy's `connect` pool event passes them.
   SQLAlchemy has no API for a connection's socket, and the records need it to
   show whether a database reconnect reused or closed an HTTP connection's
   socket. The listeners never read or write through the socket or the driver
   connection, and import no driver.
4. **Alembic revisions** (`migration-revision`), `migrations/*/versions/*.py`.
   Revisions are where schema changes belong, and Alembic generates them, so
   the check doesn't scan them. Ruff skips the same files (`extend-exclude` in
   `pyproject.toml`).

A new exception is a rule change: add a `[[rule.exception]]` entry to the rule
in `rules/registry.toml`, explain here why SQLAlchemy or Alembic can't do the
job, and get it reviewed as one. `rules/` is code-owned
(`api.process.rule-machinery-code-owned`).

### Out of scope

Redis (`policyengine_api/runtime_cache/`) is a key-value cache, not a
relational database. This rule does not cover it.

### Related rules

- `api.data.runtime-sql-confined`: raw SQL stays in the data-access layer.
- `api.services.no-direct-queries`: services never query or open connections
  themselves; they call the data-access layer.
- `api.v2.single-orm-layer`: v2 models use SQLModel, with no second
  SQLAlchemy ORM layer.
- `api.migration.alembic-v1-qualified` and `api.migration.alembic-v2-qualified`:
  CI applies the v1 and v2 revisions to disposable MySQL and Postgres
  databases, and checks v2 for schema drift.
- `api.migration.alembic-autogenerated-only` (doc-only): revisions are
  autogenerated, never hand-written.
- `api.startup.no-import-side-effects`: importing v2 modules, starting up and
  serving a request open no network connections.

## API v1 database targets

Alembic manages the API v1 MySQL schema only. The local SQLite database is a
temporary application cache and is deliberately outside Alembic's lifecycle.
Every Alembic command must therefore receive an explicit MySQL URL:

```bash
export ALEMBIC_DATABASE_URL="mysql+pymysql://..."
uv run alembic -c alembic-v1.ini upgrade head
```

The v1 configuration is `alembic-v1.ini`; its revision tree is `migrations/v1`.
Do not put a database URL in the configuration. Keeping it without a default
prevents an omitted environment variable from silently migrating the wrong
database.

## Separate v1 and v2 migration domains

The two migration domains are mechanically independent:

| Domain | Configuration | Revisions | Database | Target metadata |
| --- | --- | --- | --- | --- |
| API v1 | `alembic-v1.ini` | `migrations/v1` | Cloud SQL MySQL | existing v1 declarative metadata |
| API v2-alpha | `alembic-v2.ini` | `migrations/v2` | Supabase Postgres | reviewed `SQLModel.metadata` only |

Never point `alembic-v1.ini` at Supabase, point `alembic-v2.ini` at Cloud SQL,
append v2 revisions under `migrations/v1`, import v1 metadata into the v2
environment, or use both Alembic and Supabase CLI schema migrations as
authorities for the same application tables.

## API v2-alpha database targets

This is the isolated Supabase/Postgres migration domain with a separate revision chain;
it is never a v1 Cloud SQL target.

Every v2 command requires an explicit, secret-supplied migration URL using a
Postgres dialect and the Psycopg 3 driver, for example
`postgresql+psycopg://...`. The v2 environment must not read
`ALEMBIC_DATABASE_URL`, infer a URL from v1 or runtime settings, select SQLite
under `FLASK_DEBUG`, or fall back to local Postgres. Missing, MySQL, SQLite, or
otherwise non-Postgres targets fail before any migration operation and without
printing the URL.

A command against a persistent Supabase environment must also verify its
declared environment and project reference against the approved target
configuration. Deployment obtains both non-secret values from controlled
GitHub Environment variables; local administrative commands must obtain and
supply the same values from the approved operator inventory. Concrete target
identifiers must not be committed as defaults or application target maps.
Before baseline generation or the first upgrade, it must require a successful
freshness qualification proving that the target contains no application
tables, Alembic history, or predecessor data. Missing, mismatched, ambiguous,
or non-fresh qualification stops the command; never drop, reset, reconcile,
adopt, or stamp the target automatically.

The sole exception is the completed pre-activation v2 baseline compaction. The
dedicated v2 target was still dormant, its complete row audit found only the
two known synthetic validation rows, and a recoverable ignored backup was
created. The old v2 chain then downgraded its own application schema to
`base` before any old revision file was removed. A new parentless baseline was
autogenerated from the complete current SQLModel metadata and qualified before
being applied. This is not permission to rewrite later applied history: never
repeat it once v2 contains retained domain data or serves production traffic,
never stamp across a compaction, and never apply it to v1 or Supabase-managed
schemas and Storage.

Only a separate, explicit disposable-test mode may omit Supabase identity. It
is limited to an isolated Postgres database created for local or CI migration
lifecycle tests and must be rejected for staging, production, or any other
persistent target.

The v2 environment imports the controlled v2 table-model package before
exposing `SQLModel.metadata`. That metadata is the authoritative application
table set; do not maintain a second exact table-name allowlist. Targeted
validation must reject known v1-only names, `runtime_bundles`, and standalone
population tables. Review every autogenerated table change, and compare the
live schema directly with the complete SQLModel metadata during the migration
lifecycle.

## Table privileges

The table privileges of the managed v2 database roles are declared in
`policyengine_api/data/v2/privileges.py`, not in Alembic revisions: revisions
stay generated-only, the simulation API's role name differs per environment,
and a revision runs once per database, so it can't repair drift.

| Role | Used by |
| --- | --- |
| `policyengine_v2_runtime` | The Public API on Cloud Run |
| `policyengine_v2_catalog_writer` | `scripts/publish_v2_metadata_catalog.py` |
| `policyengine_stage12_<environment>` | The simulation API and its Modal worker, on the temporary comparison-run tables |
| `policyengine_v2_simulation_service` | The simulation API on Cloud Run: creates simulations, reports, their runs, budget-window runs and household jobs, and reads the policy, dynamic, household and catalog rows a run needs. It updates only the status, Modal call ID, error and completion columns of the runs and household jobs whose Modal calls it starts, and the status, error and completion columns of a budget-window run, which it fails at once when Modal refuses the calls of the window's first years |
| `policyengine_v2_modal_worker` | The simulation API's Modal workers: write their runs' and household jobs' status and results, and budget-window runs' status, and read the rows a run needs. It updates only a run's status, Modal call ID, error, time and result columns, and a budget-window run's status, error and time columns: each year's coordinator starts the window's next unstarted year when its own year finishes, the last year to finish marks the window succeeded, and a failed year fails it. The workers' code, not the database, keeps a worker to its own run |

Every v2 table has an entry for every role, so "no access" is a decision, not
an omission. A privilege is declared on the whole table, or with
`update_columns(...)` on only the columns it names; PostgreSQL then refuses a
statement that sets any other column, so neither simulation API role can
change what a run is. A role never holds both kinds of `UPDATE` on one table:
the whole-table one would let it set every column. The migration role owns every table and isn't listed. Three rules
check the declarations:

- `api.v2.runtime-privileges-declared`: a unit test reads each connector
  module and fails when it needs a privilege its role isn't declared to hold.
- `api.v2.runtime-privileges-tested-as-runtime-role`: the cross-database
  integration tests run the v2 user services and the parameter tree read as
  `policyengine_v2_runtime`, catalog publication as
  `policyengine_v2_catalog_writer`, and the comparison-run services as
  `policyengine_stage12_test`, holding only their declared privileges.
  `tests/integration/test_v2_simulation_role_privileges.py` runs the
  simulation API's writes as its two roles; their code lives in the simulation
  API's repository. `tests/integration/test_v2_household_calculation_reads.py`
  reads the household jobs they write through the household calculation
  service as `policyengine_v2_runtime`.
- `api.v2.deployed-privileges-match`: every deploy runs
  `scripts/reconcile_v2_privileges.py apply` right after the schema upgrade,
  then `verify`, before the catalog is seeded.

`apply` grants each declared privilege a role lacks, as one `GRANT` per role
and table and one per column privilege. It never revokes: it reports
privileges the file doesn't declare, on whole tables or on columns, and the
projects' default privileges, in the job summary. It grants nothing when a
declared role or table is missing. `verify` checks each column of a column
privilege with `has_column_privilege`, and fails when a role holds the same
privilege on the whole table. The roles themselves are provisioned outside
the repository; `--create-missing-roles` is accepted only for the disposable
test database.

A pull request may declare a role before an operator creates it by listing it
in `ROLES_AWAITING_PROVISIONING` in `privileges.py`. While a listed role is
missing, `apply` and `verify` skip it and name it in their output and the job
summary instead of failing; once it exists, the next deploy grants and checks
its privileges. Remove the role from the set once it exists in staging and
production, so that its absence fails the deploy again.

The declarations include write privileges for code paths production doesn't
turn on: the dual-write copies into `legacy_policy_mappings` and
`legacy_household_mappings`, and the writes behind the native `/v2/policies`
and `/v2/households` routes. Narrow them when those tables are removed.

When a pull request adds or changes a v2 table, or a connector's use of one:

1. Update the table's entry in `privileges.py` for every role.
2. Run `make test`, which includes `tests/unit/v2/test_privilege_manifest.py`.
3. Run the integration tests as the managed roles against disposable
   PostgreSQL:

   ```bash
   export V2_MIGRATION_DATABASE_URL="postgresql+psycopg://.../policyengine_v2_alembic_test" \
     V2_ALEMBIC_DISPOSABLE_TEST=1 DEPLOYMENT_ENVIRONMENT=test
   uv run alembic -c alembic-v2.ini upgrade head
   uv run python scripts/reconcile_v2_privileges.py apply --create-missing-roles
   uv run python scripts/reconcile_v2_privileges.py verify
   uv run pytest -q tests/integration/test_v2_user_identity_persistence.py \
     tests/integration/test_v2_stage12_comparison_persistence.py \
     tests/integration/test_v2_metadata_routes.py \
     tests/integration/test_v2_catalog_publication.py \
     tests/integration/test_v2_catalog_publication_pruning.py \
     tests/integration/test_v2_simulation_role_privileges.py \
     tests/integration/test_v2_household_calculation_reads.py \
     tests/integration/test_v2_privilege_reconciliation.py
   ```

Never grant privileges by hand in staging or production; they reach those
databases only through the deploy step, after review. The unit test reads
model names in connector modules, so it misses raw `text()` SQL and SQL issued
outside `database_connectors/`; the integration tests catch those.

## V2 application-data migrations

Alembic is also the sole authority for intentional migrations of retained v2
application data. Every such revision must originate from the same mandatory
autogeneration command used for schema revisions:

```bash
uv run alembic -c alembic-v2.ini revision --autogenerate -m "<description>"
```

Do not create a blank revision and add `bulk_insert`, SQL strings, ORM calls,
or other data operations by hand. A concrete data-migration requirement must
provide a reviewed generation source capable of producing deterministic and
reversible operations. If safe autogeneration is unavailable, invoke the human
decision rule above instead of maintaining speculative migration machinery.

The v2 baseline contains no reference-data operation, desired-state row
declaration, comparator, or synthetic validation row. Future retained-data
migrations still require a concrete reviewed generation source; do not add a
speculative general-purpose data-migration framework merely to exercise the
policy.

`alembic check` for v2 must detect schema drift.
Application startup, model import, project provisioning, and external
infrastructure provisioning must never call `create_all`
(`api.data.sqlalchemy-and-alembic-only`), create or stamp application tables,
or mutate versioned application data. The Supabase CLI is
not an application schema or seed migration authority.

Canonical metadata catalogs derived from the exact installed country and
`policyengine` packages are not hand-authored migration data. A later-stage,
explicit deployment seeder may materialize those package-derived rows after
`alembic upgrade head` when its reviewed contract requires transactional,
idempotent row-only behavior, recorded source package versions, and fail-closed
handling of partial catalogs. Such a seeder must perform no DDL, must not run at
application startup, and must not transform or delete retained domain data;
those operations remain Alembic migrations. Catalog pruning, below, is the one
exception.

Migration credentials remain separate from future runtime credentials. The
migration identity may create and alter the v2 application schema; the runtime
identity must not. Neither credential nor a secret-bearing URL belongs in an
Alembic INI file, log, committed environment file, generated artifact, or
revision.

### Catalog pruning: the seeder's one deletion

Catalog publication (`scripts/publish_v2_metadata_catalog.py`, run by the
release workflow's seed jobs as `policyengine_v2_catalog_writer`) deletes
package-derived rows of older catalog versions. Each stored version costs
about 550 MB per environment, mostly its current-law parameter values. The
code is `policyengine_api/data/v2/catalog/publication_pruning.py`, called
from `publish_catalog` in `publication.py`.

Every publication sets `tax_benefit_model_versions.catalog_last_published_at`
for each version it publishes, new, unchanged or restored, in its
transaction. After the publication transaction commits, publication keeps,
for each country's model, the version it published or republished (the
installed one) and the two most recently published other stored versions
(by `catalog_last_published_at`, or `created_at` where that is null, then
`created_at` and version text). Two are kept because the release workflow
seeds before it deploys and puts the previous revision back when promotion
fails: after one failed promotion, or a rollback to an older version, the
version still serving is one of them. Two consecutive failed promotions
followed by a third release can still prune the serving version. The rule
is decided in one function, `catalog_versions_to_prune`.

It chooses every other stored version of that model whose
`catalog_values_pruned_at` is null, and prunes at most two of them per run
(`MAX_CATALOG_VERSIONS_PRUNED_PER_RUN`), the oldest created first; the
evidence counts the rest (`catalog_versions_left_to_prune`), which later
publications prune. For each, it runs one transaction that takes the
publication advisory lock, reads the model's stored versions again, skips the
version if the rule no longer chooses it, and otherwise deletes exactly:

- the version's current-law `parameter_values`: rows of the version's
  parameters whose `policy_id` and `dynamic_id` are both null;
- the version's `parameter_tree_children` rows;
- the version's `parameter_search_files` rows;

and sets the version's `catalog_values_pruned_at` to the current time. It
never deletes or changes any other row: not `parameters` (deleting one
cascades to every value of it, saved reforms' included), not the
`tax_benefit_model_versions` row apart from that column, and not
`parameter_nodes`, `variables`, `regions`, `datasets`, `policies`,
`dynamics` or any `parameter_values` row with a `policy_id` or `dynamic_id`.
A transaction that raises an exception, of any kind, rolls back that
version alone; the failure is reported in the command's evidence and on
stderr, the command still succeeds, and the next publication tries again.

The deleted rows are rebuilt from the packages, not lost: when publication
runs for a version whose `catalog_values_pruned_at` is set (a release that
installs it again), it inserts the version's current-law values from the
installed packages and clears the column inside the publication transaction,
before the usual exact comparison of the stored version, and writes the
version's parameter tree and search file as it does for a version that has
none. The rows it writes equal those a first publication of the version
writes, with the same value IDs. Until then the metadata routes that serve
the deleted rows answer 404 for that version, with `Cache-Control: no-store`,
or 503 when it is the version the serving revision runs.

The catalog writer holds `DELETE` on the three tables and `UPDATE` on
`tax_benefit_model_versions` for this (`privileges.py`). Pruning runs no DDL;
revision `334859ef4fec` added the nullable `catalog_last_published_at` and
`catalog_values_pruned_at` columns, autogenerated with no post-generation
corrections apart from `ruff format`.

Its downgrade drops both columns, and with them the record of which versions
are pruned: a pruned version then looks complete to the parent revision's code,
which serves it with no current-law values and fails the exact comparison if
it publishes that version, with nothing to restore it. Downgrading past the
revision is therefore safe only while no version is pruned (no
`tax_benefit_model_versions` row has `catalog_values_pruned_at` set).
From the head, such a downgrade first runs the later revisions' downgrades:
`970be5d29283`'s drops `user_type_changes` with every recorded change (see
"API v2 user type changes"), `617f531f1506`'s needs no user to be an author
or an admin (see "API v2 user types"), and `1356f658347d`'s needs
`simulations` empty (see "API v2 simulation runs").
Otherwise restore the versions the target code may install or serve first, by
publishing each with this revision's code, as the Stage 9 runbook's rollback
section describes. Production downgrades are never automatic in any case.

The rule that the serving revision must work with the database changed on
its own (see "CI/CD behavior") has one accepted exception here. During the
first release that includes pruning, the seed job prunes while the previous
revision, whose code doesn't read `catalog_values_pruned_at`, still serves.
Until that release is promoted, and until the next successful release if
promotion fails, the previous revision answers a request naming a pruned
version in `policyengine_version` on `/v2/parameter-values`,
`/v2/model-catalog/parameters` and `/v2/model-catalog/variables` with a 200
holding no current-law values, `Cache-Control: public, max-age=86400` and an
`ETag`. The maintainers accepted this for that one release, because nothing
in production calls these routes with an older version until the v3 switch.
Later releases' previous revisions read the column and answer 404 (503
before issue #4243). The Stage
9 runbook's "Pre-activation sequence" describes the window.

The maintainers' approval of this exception is the review of the pull request
that added it. Deleting from another table, deleting another kind of row, or
deleting rows that publication can't rebuild from the installed packages
needs the same human migration decision.

### Fresh database qualification

Use a disposable schema named `policyengine_alembic_test` on local MySQL, then
run the lifecycle integration test:

```bash
ALEMBIC_DATABASE_URL="mysql+pymysql://.../policyengine_alembic_test" \
  uv run pytest tests/integration/test_alembic_mysql_lifecycle.py -q
```

The test must upgrade from an empty schema, run `alembic check`, compare the
live schema with the ORM metadata, downgrade one revision, and upgrade to
`head` again. Its host and schema-name checks prevent it from running against a
shared or deployed database.

### CI/CD behavior

- Pull requests first detect whether the v1 Alembic surface changed. Relevant
  PRs invoke `.github/workflows/alembic-v1-check.yml`; unrelated PRs skip it.
- Every merge to `master` runs the reusable disposable-MySQL qualification next
  to lint, regardless of which paths changed. The release commit's run skips it
  only when `check-release-commit` confirms that the release commit changes
  nothing but release files and that the merge commit's run passed it
  (`.github/release_commit.py`); otherwise the release run runs it again.
- The release migration job runs before either staging deployment. It refuses
  unversioned or invalid history, takes a backup only when revisions are
  pending, upgrades under the advisory lock, and requires zero post-migration
  drift.
- In each environment the v1 release migration and the v2 seeding job
  (`seed-v2-database.yml`, which upgrades the v2 schema and publishes the
  catalog) run side by side: the v1 job connects only to Cloud SQL and the
  seeding job only to the v2 database. Each Cloud Run candidate deploy needs
  both, so a candidate is never built until both databases are upgraded. When
  one of them fails, the release stops with the other already applied; the
  serving revision must work with either database upgraded on its own.
- Database credentials and derived URLs must never be printed. The application
  runtime account must not be granted schema-migration privileges.
- Production downgrades are never automatic. MySQL DDL is non-transactional, so
  rollback means application compatibility plus a reviewed forward fix or a
  database restore.

deployed MySQL databases do not. Integration tests cover both fresh and
production-shaped schemas and verify that `execution_id` becomes non-nullable.

### API v2 compact baseline native-enum cleanup

Revision `f5ef4347cb2a` was autogenerated from the complete reviewed SQLModel
metadata after the audited pre-activation v2-only reset. It has no parent and
directly represents the current schema; the superseded development revisions

### API v2 countries rows

Revision `fb1a3e40d3d6` was autogenerated after adding the `countries` table
and replacing the US-and-UK checks on `users.primary_country` and on the
`country_id` of households, policies and the four user association tables
with foreign keys to it. It contains one hand-written operation: it inserts
the `uk` and `us` rows, both household and society-wide capable, between the
generated table creation and the generated foreign keys, which otherwise fail
on any database whose rows already name either country. The rows are exactly
the values the replaced checks allowed. The generated downgrade removes them
with the table, and its restored checks fail if any record names another
country.

Inserting rows is a data operation, which this skill otherwise forbids. The
maintainers approved this insert as a one-off exception, because the new
foreign keys need the rows in the same revision. Unit tests pin the
operation, and the v2 Postgres lifecycle test covers an upgrade that keeps
existing rows, the downgrade, a downgrade refused by another country's
records, and the re-upgrade.

The table must list exactly the countries in
`policyengine_api/supported_countries.py`: the Public API refuses to start
when they differ (`policyengine_api/startup_country_check.py`). Listing
another country later needs a revision that inserts its row, and the same
human migration decision. The deploy runs that revision before it starts
the new release, so instances of the previous release that start afterwards,
and a rollback to it, refuse to start until the revision is downgraded. The
module docstring of `supported_countries.py` lists the other checks a new
country must widen.

### API v2 UK area impact map coordinate removal

Revision `e86f19a6c4da` was autogenerated, with `--rev-id e86f19a6c4da`, after
the `x` and `y` fields were removed from the `ConstituencyImpact` and
`LocalAuthorityImpact` models, and generated again on top of each revision
that reached `master` first: the countries revision `fb1a3e40d3d6`, then the
catalog format 2 revision `f5c1d9b4685b`. It has no post-generation
corrections. Its
upgrade drops `x` and `y` from `constituency_impacts` and
`local_authority_impacts`; its downgrade adds them back as required integers
without a server default, as the baseline created them.

The columns held hex-map positions, which nothing needs: the app draws its
maps from its own layout files. The Stage 12A revision kept every column that
the previous Public API revision maps, so that revision keeps working during
the deploy window and after an application rollback
(`docs/migration/stage-12a-user-login.md`). This revision drops four columns
that the previous revision maps, which is safe because that revision can't
read or write either table: no managed database role holds any privilege on
them (`policyengine_api/data/v2/privileges.py`), and no Public API code reads
or writes them. The lifecycle test
`test_area_impact_coordinate_removal_changes_nothing_else` checks that these
four columns are the only difference from the catalog format 2 revision's
schema.

The dropped values are not recoverable. Adding a required column fails on a
table that has rows, so the downgrade works only while both tables are empty.

### API v2 simulation runs

Revision `1356f658347d` (parent `334859ef4fec`) was autogenerated after these
model changes:

- `simulations` keeps only what to calculate. Its execution columns
  (`status`, `error_message`, `started_at`, `completed_at`,
  `household_result`) move to the new `simulation_runs`, one row per run with
  the catalog version, country package version and PolicyEngine.py version it
  used, and its Modal call ID; `output_dataset_id` is replaced by the run's
  output file (`output_uri`, `output_sha256`).
- A report run compares one pair of simulation runs: `report_runs` names its
  `baseline_simulation_run_id` (required) and `reform_simulation_run_id`
  (empty for a household report with only a baseline), each a foreign key to
  `simulation_runs` with `RESTRICT`. The parts of an economy comparison that
  had no result table are typed: `report_runs` gains the baseline's and
  reform's cliff gap and share (four nullable numbers, checked to be set
  together), the SPM receipt (`spm_provenance`, `jsonb`) and the data release
  (`data_version`). The new `labor_supply_responses` holds one row per report
  run (the earnings changes from the income and substitution effects and their
  total, the revenue change, the two relative responses, and baseline, reform
  and changed weekly hours split into the two effects), and the new
  `labor_supply_decile_responses` one row per report run and income decile.
- `poverty` and `inequality` belong to a simulation run (`simulation_run_id`);
  the other result tables belong to a report run and name the two simulation
  runs they compare (`baseline_simulation_run_id`, `reform_simulation_run_id`);
  each of their rows is unique within its report run. `aggregates` and
  `change_aggregates` are unchanged.
- The result tables gain the economy output's fields that had no column: the
  winner, loser and no-change shares of `congressional_district_impacts`, and
  the UK disclosure control fields (`disclosure_tier`, checked to be
  `reported` or `approximate`, and the four `_lower`/`_upper` interval bounds)
  of `constituency_impacts` and `local_authority_impacts`. The detailed budget
  names neither a program's entity nor whether it is a tax, so
  `program_statistics.entity` and `is_tax` become nullable.
  `decile_impacts.decile_variable` names the variable that groups households
  when it is not the income variable's own deciles (for example
  `household_wealth_decile`), and `poverty.filter_group` names the group a
  filter selects (`child` for `age`); both join their table's unique key.
- `report_runs` gains its Modal call ID.
- Budget windows: a simulation run calculates one `year`, which joins the
  index for a simulation's newest successful run. Each year of a budget
  window is a report run naming the two simulation runs it compares; the
  simulation service gives each year simulations of that year, or reuses
  succeeded runs, and the report's own two simulations are its first year's.
  `reports.budget_window_size`
  (1 to 75 years, an economy report with a year, ending by 2200) marks a
  budget-window report. The new `budget_window_runs` holds one row per
  calculation of one: its report, catalog version, trigger, whether its years
  calculate their simulations again (`recalculate`), status, error and times.
  `report_runs.budget_window_run_id` and `year` name the window run and year a
  report run calculates, at most one report run per year of a window run; a
  composite foreign key keeps it to a window run of the same report, and
  deletes it with the window run (`CASCADE`), as deleting a report deletes its
  runs.
- `household_jobs` calculates one household (`household_id`) for one `year`
  under one policy, and records its catalog and package versions and its
  Modal call ID.
- The new columns that name the Public API's rows are foreign keys with the
  delete rules the same columns have on `simulations`:
  `simulation_runs.tax_benefit_model_version_id` and `dataset_id` (`RESTRICT`)
  and `region_id` (`SET NULL`), `household_jobs.household_id` and
  `tax_benefit_model_version_id` (`RESTRICT`), and
  `budget_window_runs.tax_benefit_model_version_id` (`RESTRICT`), 20 keys
  between the two services' tables in all. `reports.user_id` gains an
  index, which account deletion's `SET NULL` searches. Each service writes only
  its own tables, and the foreign keys between them stay: PostgreSQL checks
  each named row when a row is written, with the privileges of the named
  table's owner, so a writing role needs no privilege on the named table.

Missing values in the unique keys of `poverty`, `decile_impacts` and
`program_statistics` count as equal (`NULLS NOT DISTINCT`, which PostgreSQL
supports from version 15).

It has three post-generation corrections of one kind, each commented in the
revision: `simulation_runs.status` reuses the `v2_simulation_status` type the
baseline created for `simulations.status`, and `budget_window_runs.status` and
`trigger` reuse the baseline's `v2_report_run_status` and
`v2_report_run_trigger`. The generated `create_table` would create each type
again and fail, so each column uses `postgresql.ENUM(..., create_type=False)`.

It was generated on `c614b6bcccfc`. When `master` gained the catalog pruning
revision `334859ef4fec` on the same parent, its `down_revision` moved to
`334859ef4fec`; generating it again from that revision gives the same
operations, apart from their order and these corrections.

The upgrade adds required columns without server defaults to `household_jobs`,
`report_runs` and the result tables, so it needs them empty, as they are while no managed
role holds a write privilege on them; on a table with rows it fails, and the
deploy stops before anything changes. The downgrade restores required columns
of `simulations` and the result tables the same way, so it needs
`simulations` empty, which leaves no run or result row either; it drops
`household_jobs`' new columns with their values. The previous Public API revision keeps working at this revision:
none of its roles can read or write a table the revision changes, except the
catalog writer, which only counts the rows of `simulations`, `reports` and
`report_runs`.
`tests/integration/test_alembic_v2_simulation_runs.py` checks that the
revision changes no other table, and downgrades and upgrades it again.

The name `simulation_runs` is also a v1 Cloud SQL table. The v2 metadata
validation (`policyengine_api/data/v2/metadata_validation.py`) now treats it as
a name the two databases share, as it does `simulations`.

### API v2 saved-item keys

Revision `81b728a088e7` (parent `1356f658347d`) was autogenerated, with no
post-generation corrections, after `user_report_associations.report_id` and
`user_simulation_associations.simulation_id` became foreign keys to `reports`
and `simulations`, both `ON DELETE RESTRICT`. The simulation service writes
`reports` and `simulations`, and, as for the keys in "API v2 simulation
runs", the keys between the two services' tables stay: the database refuses a saved report or
simulation that names a missing one, and a report or simulation that a saved
item names can't be deleted. A saved item that names only its v1 report or
simulation is unaffected. No role needs a new privilege: PostgreSQL checks a
saved item's insert or update as the owner of `reports` or `simulations`,
and a delete from those tables as the owner of the saved-item table, and the
migration role owns all four.

Adding a key checks every existing row, so the upgrade fails inside its
transaction, changing nothing, while a saved item names a missing report or
simulation. Before deploying it to an environment, count those rows read-only:

```sql
SELECT count(*) FROM user_report_associations AS link
WHERE link.report_id IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM reports WHERE reports.id = link.report_id);
SELECT count(*) FROM user_simulation_associations AS link
WHERE link.simulation_id IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM simulations WHERE simulations.id = link.simulation_id);
```

Both were 0 in staging and production on 2026-11-10. The downgrade drops the
two keys and nothing else. While a saved simulation names a simulation, that
row can't be deleted, so emptying `simulations` for a downgrade past
`1356f658347d` means downgrading this revision first, or clearing the saved
simulations' `simulation_id` (deleting a saved simulation that has no
`legacy_simulation_id`, which its check requires).
`tests/integration/test_alembic_v2_saved_item_keys.py` checks the refused
inserts and deletes, the refused upgrade and the downgrade.

### API v2 user types

Revision `617f531f1506` (parent `81b728a088e7`) was autogenerated after
`users.user_type` gained the types `author` and `admin`, after `standard`.
Each signed-in user is `standard`, `author` or `admin`, and each type has
every permission of the types before it in `UserType`.

Alembic compares check constraints by name only, not by condition (PostgreSQL
stores `IN (...)` as `user_type::text = ANY (ARRAY[...])`), so a check whose
condition changes under the same name goes undetected. The
check that allows the four types is therefore named
`ck_users_user_type_allowed`, and autogenerate turns the change into a drop of
`ck_users_user_type` and an add of the new check. The revision has no
post-generation changes. Give any later change to a check's condition a new
name in the same way.

It was generated on `1356f658347d`. When `master` gained the saved-item keys
revision `81b728a088e7` on the same parent, its `down_revision` moved to
`81b728a088e7`; the two revisions change different tables, so generating it
again from there gives the same operations.

The upgrade only widens what the check allows. The previous Public API
revision keeps working until a user is given the `author` or `admin` type: its
`/v2/me` responses allow only `unauthenticated` and `standard`, so they fail
with 500 for such a user, and `PATCH /v2/me` and `/v2/me/upgrade` fail only
after their change or merge has committed. Give those types only once no
deployment, rollback included, runs the previous revision. The downgrade restores the check that
allows only `unauthenticated` and `standard`, so it fails while any user is an
author or an admin. `test_user_types_revision_changes_only_the_user_type_check` in
`tests/integration/test_alembic_v2_user_types.py` checks that nothing else
changes, and
`test_user_types_revision_accepts_authors_and_admins_until_downgraded` that
the downgrade refuses while either type is stored.

The resolved user's type is converted to `UserType` on every signed-in
request. A later revision that adds a type must say that rolling the
application back below it fails every signed-in request of a user with the new
type, not only `/v2/me`.

### API v2 user type changes

Revision `970be5d29283` (parent `617f531f1506`) was autogenerated after the
`UserTypeChange` model was added, and has no post-generation changes. It
adds `user_type_changes`, one row per change of a signed-in user's type: the
user (`CASCADE`), the admin who made it (`SET NULL`; empty for the type
script), the previous and new types (each `standard`, `author` or `admin`,
and different), and the `source`, `admin_route` or `script`. An index on
`(user_id, created_at)` serves a user's history, and one on
`changed_by_user_id` the `SET NULL` that every user deletion runs. The runtime role may read and
insert its rows, never update or delete them; a user's deletion removes them
through the foreign key, which PostgreSQL runs with the table owner's
privileges.

The previous Public API revision never uses the table. The downgrade drops it
with every recorded change. `test_user_type_changes_revision_adds_only_its_table`
in `tests/integration/test_alembic_v2_user_types.py` checks that nothing else
changes.

### API v2 catalog SPM availability

Revision `0c136a278f29` (parent `970be5d29283`) was autogenerated, with no
post-generation corrections, after `tax_benefit_model_versions` gained the
nullable JSON column `spm_availability`. It was generated on the saved-item

### API v2 withheld area codes

Revision `1e1e3f079f2c` (parent `0c136a278f29`) was autogenerated, with
`--rev-id 1e1e3f079f2c`, after the `WithheldAreaCode` model was added. It
creates `withheld_area_codes`, one row per UK area that disclosure control
withheld from a report run's local-area results: the report run (`CASCADE`),
its baseline and reform simulation runs (`RESTRICT`, as the other comparison
result tables have), the `area_type` (the new native enum `v2_uk_area_type`,
`constituency` or `local_authority`) and the area's `code`, unique per report
run and area type. Every local-area run that succeeds records its list, so a
succeeded run without rows withheld none, and a withheld area has no row in
`constituency_impacts` or `local_authority_impacts`. The Modal worker role
may read and insert its rows, never update or delete them, and the runtime
role may read them; the reconcile step after each schema upgrade grants
them.

It has one post-generation correction, for reversibility: Alembic's
generated downgrade drops the table but leaves the enum type, so the
downgrade also drops `v2_uk_area_type` after the table, as `439303be14fe`
does for its enums. Without it, upgrading again after a downgrade fails on
the existing type. The revision writes no data, and the previous Public API
revision, which doesn't map the table, keeps working at it. The downgrade
drops the table with its rows. `tests/integration/test_alembic_v2_withheld_area_codes.py`
checks that nothing else changes, that the downgrade removes the type and an
upgrade works again, and the table's keys and delete rules.
